# v6.4 비교 결과

**800ms 복구 중앙값 감소는 두 후보 부팅에서 관찰됐지만, 200ms와 일반 작업까지 동시에 개선했다는 목표는 충족하지 못했다. v6.4를 전체 성능 개선판으로 채택하기는 이르다.**

가까운 v6.2 부팅과 비교하면 800ms 중앙값은 각각 25.19%, 35.32% 낮았다. 반면 200ms 중앙값은 12.24%, 135.97% 높았고, bursty 1024 KiB 완료 시간은 4.47%, 6.31% 길었다. pinned CPU 시간은 2.45%, 6.05% 낮아졌으므로 일반 작업 전체가 악화된 것은 아니다. 각 항목에 이득과 손해가 함께 나타났다.

v6 기준의 200ms 중앙값도 3.301~44.392ms로 크게 달랐다. 따라서 위 수치는 이번 인접 부팅의 관찰 차이이며, 패치의 인과 효과나 통계적 유의성을 확정하는 값은 아니다. v6.4의 800ms 중앙값은 세 v6 기준 부팅보다 모두 낮았지만, 200ms는 중간 v6 기준보다 두 번 모두 높았다.

정확한 853ms 조건 70회에서는 1초 초과가 재현되지 않았고 최대는 65.591ms였다. v6.4만 보면 최대값은 18.477ms와 61.994ms였다. 이는 과거 1초 지연이 해결됐다는 증거가 아니며, 과거 사례의 직접 원인은 아직 확정하지 못했다.

v6 → v6.2 → v6.4 → v6 → v6.4 → v6.2 → v6 순서의 새 부팅 7회, 측정 357회다. v6는 수정된 기준 커널이며, 이 비교는 hot 패치의 추가 효과를 평가한다.

11월 25일 첫 시도(c1~c3)는 호스트 덮개 닫힘에 따른 절전으로 중단돼 별도로 보존했다. 아래 표는 재개 후 d1~d7만 사용한다. 자동 절전 방지 요청을 사용했으며 CPU 전원 정책과 affinity 설정은 변경하지 않았다.

각 부팅에서 명목 200ms·800ms를 각각 10회(실제 대기는 ±64ms), 정확한 853ms를 10회 측정했다. 일반 작업은 bursty 각 버퍼 5회, steady와 pinned 각 3회다. 모든 부팅의 실제 대기 순서와 프로그램 해시를 대조했다.

복구 값은 affinity 확장 시작부터 CPU 표본상 네 CPU의 작업 배치가 50ms 유지되기 시작한 시점까지다. 커널의 실제 이동 시각이나 CPU가 연속 실행된 시간을 뜻하지 않는다. 진단용 ftrace는 이 성능 비교에서 사용하지 않았다.

## v6.4와 v6.2의 가까운 부팅 비교

## 조건 점검과 해석 범위

- 커널 이미지, 서로 다른 부팅 ID, LOCALVERSION을 제외한 설정, 프로그램 해시, 실행 횟수, 대기 순서를 검증했다.
- 기존 runner의 `fair_source_sha256`은 별도 원본 소스 트리를 읽는 값이다. 실행 중인 후보 구분에는 이 값 대신 부팅 이미지 해시와 각 후보 빌드 기록을 사용했다.
- 각 실행은 작업 체크섬을 검사했으며 커널 저널의 BUG/Oops/lockup 패턴 검사도 통과해야 자료를 전송한다.
- 부팅은 버전당 2~3회다. 한 부팅 안의 반복을 모두 독립 부팅으로 취급하지 않는다.
- Windows의 실제 코어 배치·주파수·열 상태·다른 작업 부하는 통제하지 않았다.
- cache miss나 hot 완화 분기의 적중 횟수는 별도로 계측하지 않았다. 시간 차이만으로 캐시 효과의 원인을 확정하지 않는다.
- 이전의 853ms 1초 초과 사례와 이번 성능 측정에는 동시 커널/호스트 추적이 없다. 해당 값만으로 원인을 확정할 수 없다.
